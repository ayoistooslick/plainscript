Objective

Prepare PlainScript for the next stage of its development as a serious general-purpose programming language.

This is NOT a request to make PlainScript specifically support one particular application.

Do NOT add features named after, hardcoded for, or tightly coupled to any specific project.

Instead, evaluate whether PlainScript is sufficiently capable for programmers to build a broad range of serious software, including projects that may involve:

- real-time systems
- browser applications
- games
- computer-vision applications
- AI-powered applications
- data processing
- networking
- APIs and backend services
- event-driven applications
- automation
- simulations
- scientific/technical software
- multimedia applications
- developer tools
- database-backed applications
- distributed systems
- applications using existing JavaScript/npm ecosystems

A future football computer-vision/referee-assistance type project is one example of the class of applications PlainScript should be capable of supporting.

It is NOT the specific target.

The goal is general capability.

First, inspect the entire compiler, runtime, standard library, CLI, tests, documentation, examples, templates, and existing interoperability system.

Do not immediately start changing code.

Determine what PlainScript can actually do today.

Audit at minimum:

Core language

- variables
- constants
- expressions
- functions
- closures
- control flow
- loops
- collections
- objects/records

- modules/imports
- scope

Runtime and execution

- promises
- async/await semantics
- concurrency
- timers
- event-driven execution
- callbacks
- error propagation
- process lifecycle
- cancellation where applicable

JavaScript interoperability

- calling JavaScript functions

- receiving JS values
- callbacks
- promises
- events
- objects
- arrays
- exceptions
- browser APIs
- Node.js APIs

Networking

- HTTP requests

- headers
- JSON
- request/response handling
- streaming where appropriate
- connection/error handling

Data and files

- filesystem access
- reading/writing files
- JSON

- environment variables
- configuration
- streams where relevant

Browser capabilities

Evaluate:

- DOM manipulation
- events
- fetch
- timers
- canvas
- animation/frame loops
- Web APIs
- browser module execution
- WebGL/WebGPU interoperability where practical

Graphics and multimedia

PlainScript should be able to participate in serious applications that use existing JS/browser ecosystems.

Evaluate interoperability with:

- Canvas
- WebGL/WebGPU
- audio APIs
- video APIs
- image/data processing libraries
- rendering libraries

AI and external services

Evaluate whether PlainScript can reasonably integrate with:

- HTTP AI APIs
- streaming AI APIs
- SDKs
- model-serving services
- external Python/JS services
- local processes/services

PlainScript does not need to implement neural-network frameworks itself.

It needs to be capable of orchestrating and integrating serious systems.

Databases

Evaluate:

- SQLite
- PostgreSQL
- other databases through existing JS/npm packages
- async database operations
- transactions
- query results
- connection lifecycle

Processes and system integration

Evaluate:

- spawning processes where supported
- communicating with processes
- CLI execution
- environment variables
- exit codes
- stdin/stdout/stderr
- integration with external tools

Package ecosystem

Evaluate whether a PlainScript programmer can realistically install and use npm packages without fighting the compiler.

Phase 2 — Identify actual blockers

After the audit, classify findings into:

A. Already works

No changes required.

B. Works, but has poor ergonomics

Improve only if the improvement is justified and does not destabilize the language.

C. Missing but important

Determine whether a language/runtime feature is genuinely necessary.

D. Better handled through JavaScript/npm interoperability

Do NOT add a new PlainScript feature just because JavaScript already provides a mature solution.

E. Experimental/nonessential

Do not implement merely because it sounds impressive.

The objective is not feature count.

The objective is real capability.

Phase 3 — General-purpose improvements

Implement only changes that materially improve PlainScript's ability to build broad classes of software.

Prioritize:

1. correctness
2. predictable semantics
3. interoperability
4. asynchronous/event-driven programming
5. networking
6. data handling
7. runtime reliability
8. developer ergonomics
9. package ecosystem compatibility
10. performance where relevant

Avoid:

- project-specific APIs
- football-specific functionality
- computer-vision-specific syntax
- proprietary replacements for npm libraries
- unnecessary language complexity
- syntax additions that merely make examples look nicer

PlainScript should remain recognizable as PlainScript.
