Comparison with TypeScript stacks

This is an engineering comparison, not a marketing claim. PlainScript is younger and has a much smaller ecosystem. The useful question is narrower: for a schema-first full-stack application, how much duplication and unchecked boundary code does each approach require?

Compared stacks

  • PlainScript + std/contract + std/db + React (this repository's flagship demo).
  • TypeScript + Zod (runtime schemas and inferred types) + tRPC (typed procedures/client).
  • TypeScript + Prisma or Drizzle (database schema, generated client, migrations) + Zod.

Actual evidence from this repository

The flagship demo's shared contract is one 16-line module: demos/contracts-fullstack/src/shared.pln. It declares one record schema, one error schema and four operations. The server and React client import those values; neither declares a parallel task model. tests/contract-errors.test.js proves that an unknown enum literal, a wrong command output and an undeclared error code are rejected before execution. tests/contract-demo.test.js runs the compiled server, logs in, creates/toggles/reads a task through validated operations, gets a typed 404 failure, restarts the process and verifies persistence. tests/db.test.js proves schema-derived tables, migration rollback and invalid-row rejection. These are executable checks, not API-shape claims.

What PlainScript genuinely offers

  1. A schema change propagates to types, runtime validation, SQLite columns, handler

    2. contracts and the browser client in one edit. The demo is 16 shared lines, with zero duplicated frontend model declarations.

  2. Typed error unions are first-class operation results, not an afterthought; the compiler

    3. rejects an undeclared failure code and matching is exhaustive.

  3. Runtime validation is not optional glue: input and both outcomes are validated by the

    4. same schema at both trust boundaries.

  4. The language is small enough to audit and emits ordinary ESM, so React, Node and npm

    5. packages remain usable without a custom bundler.

What it does not offer

Prisma-level database support, a mature auth provider integration, JSX, a bundler, a debug adapter, a large ecosystem, or a measured speed advantage over TypeScript. Variadic tuples, readonly modifiers and distributive conditional types are not implemented. Any claim that PlainScript is universally better would be false.

Reproduce the checks

npm test
cd demos/contracts-fullstack && npm install && npm run build
node ../../src/cli.js check src/shared.pln src/server.pln src/App.pln

The TypeScript alternatives are described at the level of their documented workflows; this repository does not contain an equivalent TypeScript implementation or a cross-language benchmark. That limitation is intentional and is tracked in ROADMAP.
