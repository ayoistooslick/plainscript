Cross-language interoperability

PlainScript runs on JavaScript, so JavaScript and TypeScript are the native interoperability story: import an npm package, a Node builtin, a browser API or a local .js module and the emitted ESM uses it directly. Projects in other languages need a boundary that crosses a process. PlainScript 2.2 standardised that boundary, and 2.3 adds a typed TypeScript client and deeper verification, instead of inventing a different integration for every language.

The boundary is newline-delimited JSON-RPC 2.0. A PlainScript module is served by plainscript bridge; generated clients in Python, JavaScript, TypeScript, Java, Kotlin, C, C++, Go, Rust, Ruby, PHP, C#, Swift and Dart call it over stdio or HTTP. std/bridge is the same protocol in the other direction, so PlainScript can call a Python service.

This is deliberately a process boundary, not a foreign-function interface (FFI) or a native embedding API. It works wherever the participating runtimes work, keeps crashes and memory ownership apart, and requires no compiler plugin for each host language. The trade-off is serialisation cost and no shared mutable memory; use it at module boundaries, not inside a hot loop.

The bridge serialises results with JSON; nothing becomes null, and a non-serialisable value is reported as an execution error.

Generated bindings

The output contains the manifest, protocol notes and one client per requested language. Generated clients are small and dependency-free where the language allows it; C and C++ use a header plus a generated implementation that calls the CLI, while JVM, Go, Rust, Ruby, PHP, C#, Swift and Dart clients are source files with the same request/response shape.

The repository ships scripts/verify-bindings.js, which generates every client, compiles it with the language toolchain and runs a live bridge call where the toolchain allows it. This checkout has Node, Python, C and C++ toolchains, so those are executed locally; Go, Rust, Ruby, PHP, C#, Java, Kotlin, Swift and Dart are compiled or executed by the dedicated CI job that installs them. A client that cannot be executed in a given environment is reported as skipped with the missing toolchain, never counted as a pass.

Choosing a boundary

SituationRecommended boundary
JavaScript, TypeScript, React, NodeDirect ESM import; generated .d.pln for declarations
Python service or scriptplainscript bridge + Python client, or std/bridge
C / C++ libraryKeep the library in C/C++, expose a narrow process or HTTP service; generated C client for calling PlainScript
Java / Kotlin / Go / Rust serviceRun it as a service and call over HTTP JSON-RPC; generated client
Data pipeline across languagesJSON-RPC process boundary with a versioned manifest
Hot path inside a native libraryNot solved by 2.3; native FFI/WASM embedding is a future adapter

The architecture is extensible by adding a generator to src/interop/bindings.js and a small client runtime for the language. The protocol and manifest are stable across generators; adding a language does not change the compiler.

Security and operations

  • A bridge is a local process. --http binds to 127.0.0.1 by default; put an

    • authenticated reverse proxy in front of it before exposing it to a network.

  • The bridge executes the module. Do not point it at untrusted source.
  • Params are validated against the manifest's arity and names, but a dynamic

    • language client can still send values of the wrong JSON shape. Validate business input inside the PlainScript function.

  • The child process is terminated when the client closes or exits; a crashed

    • bridge surfaces as a connection error in the client.

  • JSON has no distinction between a missing optional value and null. Model

    • absence as null or use a record with an explicit flag.

JavaScript interoperability remains the native path

Cross-language JSON-RPC does not replace direct JavaScript interop. The same release continues to support:

  • ESM and CommonJS packages through Node's resolver.
  • Node builtins and browser APIs via declare.
  • TypeScript declarations through plainscript interop.
  • React and Vite through emitted ESM and source maps.
  • Local JavaScript modules through .d.pln declarations and generated

    • boundaries.

See JavaScript interoperability for the native path, and JSX and React for components.
