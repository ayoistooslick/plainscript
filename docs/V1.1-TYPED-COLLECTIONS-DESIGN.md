# PlainScript v1.1.0: Typed Collections Design

**Status:** Design proposal  
**Milestone:** v1.1.0 · Language Depth  
**Predecessor:** Function return contracts

## Purpose

Typed collections are the next increment after return contracts. Return contracts
make a function's result visible to the checker. Typed collections make the
shape of that result useful when it contains repeated or nested values.

The feature must solve one narrow problem well: when PlainScript has a declared
collection type and a collection literal is available, the checker must verify
every element against the declared element type. This includes nested lists,
dictionaries, and declared record contracts. The implementation must not become
a general-purpose whole-program inference system in this branch.

## Proposed surface syntax

PlainScript already uses `list of T` and `dictionary of T` in record fields and
function parameter contracts. The same type expressions will be valid for local
mutable bindings by placing the annotation between the variable name and its
initializer:

```text
type User
    id is number
    name is text
done

let users as list of User is [
    { id: 1, name: "David" },
    { id: 2, name: "Samuel" }
]

let usersById as dictionary of User is {
    first: { id: 1, name: "David" },
    second: { id: 2, name: "Samuel" }
}
```

The existing `let name is value` form remains unchanged. The existing
`remember name as value` form also remains unchanged in this milestone because
`as` is already its initializer separator. Typed immutable bindings are not
needed to establish collection checking and can be designed separately without
making `remember` ambiguous.

The feature does not introduce a new collection literal syntax. Square brackets
remain list literals, and braces remain object or dictionary literals according
to their existing parsing context.

## Type model

The parser will continue to produce the existing recursive type-specification
shape:

```text
name        -> { kind: "name", name }
optional T  -> { kind: "optional", value: T }
list of T   -> { kind: "list", value: T }
dictionary of T -> { kind: "dictionary", value: T }
T or U      -> { kind: "union", values: [T, U] }
```

The checker should treat these specifications as recursive values rather than
flattening collection types to the single string `list` or `dictionary`. A
small internal `TypeRef` normalization layer may be introduced if the current
string-based inference prevents recursive comparisons. That refactoring belongs
inside the checker and must preserve existing diagnostic codes and messages for
primitive contracts.

A declared record name remains a named type. Its value is valid only when the
checker can verify an object literal against the corresponding `type`
declaration, or when the value's known type is that declared record. A plain
`object` remains intentionally less specific and accepts any object value.

## Static checking rules

When a typed binding has an initializer, the checker performs these checks:

1. `list of T` requires a list literal or a known list value. Every element is
   checked recursively against `T`.
2. `dictionary of T` requires an object or known dictionary value. Every value is
   checked recursively against `T`; dictionary keys remain unconstrained text
   keys.
3. `optional T` accepts a missing value or `null`, and otherwise checks the
   value against `T`.
4. `T or U` accepts a value matching at least one branch. Literal diagnostics
   should report the complete expected union when no branch matches.
5. A named record type checks required fields, optional fields, unknown fields,
   and each field value recursively. If a field itself has type `list of User`,
   every list element is checked as a `User` record.
6. A literal with an expression-valued element is not rejected merely because
   the expression is not yet inferable. The checker reports a mismatch only
   when the expression has a known incompatible type. Expression propagation is
   the following v1.1.0 milestone.

For example, this program must produce a field diagnostic for the second list
element:

```text
type User
    id is number
    name is text
done

make loadUsers() returns list of User
    give [
        { id: 1, name: "David" },
        { id: "wrong", name: "Samuel" }
    ]
done
```

The diagnostic should identify the collection context and element path, such as
`Return value element 2 field "id" expects number, received text.` The exact
wording may evolve, but the diagnostic must retain the existing
`PLN-TYPE-FIELD` or `PLN-TYPE-RETURN` family and point to the collection's source
range until element-level source spans are available.

## Contract propagation within this milestone

The checker should record a typed local binding's declared type in its
environment. A call to a function returning `list of User` or `dictionary of
User` should likewise retain that recursive return type rather than reducing it
to `list` or `dictionary`.

This milestone only requires enough propagation to validate collection values at
contract boundaries and to validate indexed access when the type is already
known. Indexing a known `list of T` may produce `T`, and reading a known
`dictionary of T` may produce `T`. Rich propagation through arbitrary operators,
branches, aliases, and callbacks belongs to the next expression-typing branch.

## Runtime behavior

Typed collections do not add runtime behavior. Existing generated JavaScript
already represents lists as arrays and dictionaries as objects. Runtime record
validation remains the responsibility of the existing function-entry contract
checks. The new work is static validation of literal collection contents and
preservation of recursive type information in the checker.

If a typed collection is passed to a function at runtime, the generated program
must continue to use the same contract validation path as an equivalent record
field. The design must not introduce a second incompatible runtime validator.

## Diagnostics

The implementation should add only diagnostics needed to explain collection
mismatches:

| Code | Meaning |
| --- | --- |
| `PLN-TYPE-COLLECTION` | A value is not a list or dictionary where the contract requires one. |
| `PLN-TYPE-ELEMENT` | A list element or dictionary value does not match its element type. |
| `PLN-TYPE-FIELD` | A nested declared record has a missing, invalid, or unknown field. |
| `PLN-TYPE-ARG` | A function argument does not match a collection parameter contract. |
| `PLN-TYPE-RETURN` | A return value does not match a collection return contract. |

Existing field and argument diagnostics should be reused where they already
explain the failure. New codes are justified only when they distinguish the
collection boundary from the nested value. Diagnostics should include the
expected recursive type using the existing `typeName` rendering, for example
`list of User` or `dictionary of optional text`.

## Parser and checker changes

The implementation branch should make the following bounded changes:

- Extend `let` declarations to accept `let name as Type is value` and preserve
  the parsed type on the `RememberStatement` node as `typeAnnotation`.
- Validate the annotation through the same unknown-type path used by parameter
  and return contracts.
- Replace literal-only contract validation with a recursive validator that can
  descend through `ArrayLiteral`, `InlineObjectLiteral`, and `ObjectLiteral`
  nodes.
- Store the declared recursive type on the local checker environment.
- Preserve recursive return types from function calls.
- Add focused tests for lists, dictionaries, nested records, unions, optional
  elements, invalid element values, and unknown nested contract names.
- Update the language specification and README examples only after the grammar
  and checker tests pass.

No generator changes are expected unless the existing runtime contract emitter
cannot consume recursive collection specifications. No LSP feature work belongs
in this branch.

## Explicit non-goals

This branch will not implement flow-sensitive narrowing, full operator typing,
collection mutation checking, generic type parameters, tuple types, inferred
annotations for every variable, cross-file type resolution, or advanced LSP
features. It will not attempt to prove that every possible runtime collection
value is valid. Static guarantees apply to values and expressions whose types
are known at the checking point.

## Acceptance criteria

The branch is ready for review when all of the following hold:

- A valid `list of User` literal passes static checking.
- An invalid nested record inside a list produces a deterministic diagnostic.
- A valid `dictionary of User` literal passes static checking.
- An invalid dictionary value is reported without masking unrelated diagnostics.
- Nested lists and dictionaries recurse through at least two levels.
- Optional and union element types behave consistently with existing contracts.
- A function returning `list of User` preserves that return type for a caller.
- Existing untyped programs and existing parameter contracts remain unchanged.
- Focused type tests, LSP tests, documentation checks, and the full test suite
  pass before the branch is opened.
