# PlainScript v1.1.5 Completeness Gap Analysis and Implementation Plan

## Correct milestone thesis

PlainScript **v1.1.5 is the completeness milestone**. It is not merely a trustworthiness foundation with mainstream language capability deferred to v1.2.x. The release must contain the general-purpose capabilities needed to build serious multi-file software without requiring a new domain-specific compiler feature for every application category.

> PlainScript should provide powerful general-purpose language primitives, a broad standard library, and strong JavaScript/npm interoperability. Web backends, APIs, CLIs, bots, games, automation, libraries, and database applications should be built from those primitives rather than from an ever-growing collection of one-off syntax features.

The current `main` branch is a verified trustworthiness slice, not the finished completeness release. This document is the active contract for the remaining work.

## Already implemented and retained

- Near-English declarations, functions, lambdas, records, collections, templates, control flow, errors, async syntax, modules, npm imports, CLI compilation, source maps, and an in-process LSP.
- Recursive contracts for named records, optional fields, unions, lists, dictionaries, typed returns, Promise tracking, indexes, assignments, and common expression results.
- Local dependency discovery, aliases, directory resolution, cycle diagnostics, named/aliased/namespace imports, barrel exports, SQLite/WASM, HTTP, filesystem, crypto, CLI, browser, Canvas/WebGL, WebSocket, bots, uploads, sessions, and broad runtime helpers.
- Verified regressions for collection soundness, destructuring, module export visibility, incremental LSP edits, retry failure propagation, release metadata, and the complete existing test suite.

## Remaining completeness gaps

### Language and type system

- Generic or otherwise expressive reusable types, including substitution and useful diagnostics.
- Named aliases and normalized recursive unions.
- Discriminated unions with flow-sensitive narrowing.
- Structural patterns with bindings, guards, alternatives, impossible-arm diagnostics, and useful exhaustiveness checking.
- A capable object/abstraction model: validated constructors, typed members/methods, predictable record/kind behavior, and interoperable class/object semantics.
- Typed tuple, Set, and Map contracts plus mutation checking and generic collection operations.

### Runtime and standard library

- Portable JSON/value conversion for Map, Set, BigInt, undefined, circular values, and deterministic encoding. **Implemented in this milestone.**
- Correct calendar/timezone/UTC date semantics and complete formatting.
- Async/atomic filesystem operations, directory streams, and teaching errors.
- Cancellable and streaming subprocesses with cwd/env/timeout/signal/stdio options.
- Richer HTTP request/response/options/abort/retry/stream support.
- Precise browser/package target behavior and a truthful WebGPU/Three.js interoperability contract.

### Async, errors, and resources

- Promise.any semantics, aggregate failures, loser/sibling cleanup, and structured task handles.
- Cancellation tokens/signals and timeout propagation for supported operations.
- Retry predicates, backoff/deadlines, normalized error causes, and source context.
- Background/scheduled task observation and shutdown ownership.
- Scope-based `defer`/`using`-style cleanup for streams, subprocesses, databases, caches, sockets, and schedules.

### Modules and interoperability

- A real module linker with canonical module IDs, private scopes, isolated declarations, explicit exports, stable aliases, and collision diagnostics.
- Graph-aware build/check/type analysis rather than flattened synthetic AST checking.
- Config-driven `rootDir`/`baseUrl`/`paths` resolution and manifest/lockfile reconciliation.
- Robust CommonJS/ESM/default/named/subpath/exports-condition handling and explicit Node/browser targets.

### Tooling and proof

- A real VS Code LSP client, semantic cross-file navigation, structured diagnostics, formatting integration, lifecycle/version/cancellation handling, and stable JSON output.
- Correct formatter behavior and source-map offsets through generated wrappers and bundled modules.
- Mandatory CI, packaged-consumer tests, recursive version validation, template/application matrices, real-browser proof, and clearly labelled service-backed or offline integration tests.

## Implementation sequence

1. **Shared semantic spine and module linker:** canonical graph/module IDs, per-module symbols and exports, config-rooted resolution, isolated generated module records, graph-wide diagnostics and type checking.
2. **Expressive types and structural control flow:** aliases, closed unions, explicit generic parameters/instantiation, structural patterns, guards, narrowing, impossible/duplicate/unreachable arms, and exhaustiveness.
3. **Object and collection completeness:** validated object abstractions, typed methods/members, tuple/Set/Map contracts, and mutation checking.
4. **Runtime and error contract:** normalized diagnostics/errors, JSON/date/files/process/HTTP correctness, and compatibility-preserving richer options.
5. **Structured async/resource semantics:** Promise.any, task handles, cancellation, timeout propagation, retries/backoff, structured background work, and disposal.
6. **Production tooling:** compiler-backed symbols, cross-file LSP, VS Code client, formatter modes, stable diagnostics, and source-map correctness.
7. **Executable proof and packaging:** CI, npm tarball consumer, application/template matrices, browser and service contract gates, and release integrity.

## Release gates

- `npm test`, docs checks, release checks, formatter checks, LSP/extension smoke, source-map tests, and all type/module/runtime regressions pass in CI.
- The exact npm tarball installs into a clean consumer and builds/runs a typed multi-file application with isolated modules and source-mapped failures.
- Generic types/aliases, structural matching/narrowing/exhaustiveness, object abstractions, typed collections, Promise.any/cancellation/disposal, and JS/npm interop each have positive and negative tests.
- Every advertised example/template is either executable in a deterministic matrix or explicitly annotated with its external-service requirements; compile-only proof is not presented as runtime proof.
- Versions agree across root/lockfile/compiler/grammar/changelog/LSP/VS Code/templates, and publish uses the immutable artifact that passed the gates.

## Compatibility rule

Preserve valid v1.0.363 and v1.1.x programs wherever practical. New completeness features should use unambiguous syntax and explicit diagnostics. Legacy untyped code remains permissive at dynamic boundaries, while new typed code must not silently escape through `any`.
