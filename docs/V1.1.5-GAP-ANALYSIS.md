# PlainScript v1.1.5 Gap Analysis and Implementation Plan

## Position

PlainScript v1.1.5 will be a **trustworthiness and tooling milestone**, not a broad syntax expansion. The current near-English core, records, control flow, async subset, module bundling, CLI, and regression suite are useful foundations. However, the current green test suite overstates readiness because several safety boundaries are incomplete or inconsistent.

The milestone will make the existing language dependable for serious multi-file applications while preserving valid v1.0.363 and v1.1.x behavior wherever reasonably possible. New syntax is limited to forms needed to repair existing advertised capabilities.

## Current strengths

- A substantial near-English core is implemented: variables, functions and lambdas, conditionals, loops, collections, records, templates, errors, async combinators, modules, and npm/JavaScript interop.
- Baseline contracts already cover records, optional fields, unions, nested collections, typed returns, Promise tracking, and null checks.
- Build and bundling provide deterministic discovery, aliases, directory entry resolution, cycle detection, source maps, CommonJS output, and clean CLI validation.
- Async lowering, `try`/`recover`/`finally`, HTTP timeout behavior, SQLite/WASM, filesystem/crypto helpers, and broad adapters have focused coverage.
- The suite contains useful compiler, runtime, packaging, torture, acceptance, LSP, and documentation checks.

## Critical gaps

1. **Checker soundness:** heterogeneous collections, invalid indexes, assignments, operators, nested control-flow returns, function values, and unknown interop can escape through `any`.
2. **Module correctness:** analysis flattens files into a global scope; unexported imports can pass, same-name declarations can overwrite one another, and checker/LSP/bundler do not share one module graph.
3. **Destructuring correctness:** array rest fails generation and object rest silently loses data; nested aliases, defaults, parameter targets, and assignment targets lack conformance coverage.
4. **Async reliability:** timeout races do not cancel underlying work, background failures are detached and logged, retry exhaustion is swallowed, and resources lack scope-based disposal.
5. **Developer tooling:** the VS Code package is syntax-only; ranged LSP edits are ignored; navigation is regex-based and local; diagnostics are lossy; formatting is heuristic and not exposed through LSP.
6. **Release proof:** version metadata is inconsistent, one canonical example fails checking, and most examples/templates/providers are compile-only rather than executable proof.

## Architectural decisions

- Create one semantic spine shared by parser, checker, bundler, CLI, LSP, and formatter: canonical AST nodes, symbols, source spans, diagnostics, and module graph.
- Replace flattened analysis with per-module symbol/export environments. Enforce explicit export surfaces, aliases, duplicate-binding diagnostics, deterministic resolution, and documented cycle behavior.
- Adopt a canonical type algebra distinguishing `any`, `unknown`, named records, unions, optionals, collections, Promise values, and function types. Keep dynamic interop as an explicit escape hatch rather than implicit `any`.
- Keep records and protocol-like contracts as the supported data abstraction for this release. Treat the existing class surface as constrained JavaScript interop; do not expand it into a second incomplete object model.
- Make destructuring patterns first-class AST nodes shared by declarations, parameters, assignments, and future matching. v1.1.5 implements nested patterns, aliases, defaults, and rest with correct code generation.
- Define a minimal structured async contract: normalized errors with source context, observable task handles, cancellation for supported operations, and scope-based disposal.
- Use structured diagnostics and semantic symbols for both CLI and LSP. The VS Code extension must become a real LSP client.

## Milestone scope

### 1. Semantic and module foundation

- Workspace module graph and per-file symbol/export tables.
- Visibility and alias enforcement, collision diagnostics, and cross-file checker/LSP resolution.
- Unified local/package resolution, including `file:` imports and deterministic cycle diagnostics.
- Structured diagnostics with stable codes and precise source spans.

### 2. Checker soundness

- Separate `unknown` from `any` and audit dynamic escape points.
- Preserve heterogeneous element information or issue definite mismatch diagnostics.
- Validate index, assignment, and basic operator operands.
- Traverse every nested statement body, including loops, `try`, `match`, and `finally`.
- Enforce path-aware return contracts and missing-return diagnostics.

### 3. Production-quality destructuring

- Nested array/object patterns.
- Aliases, defaults, rest elements, and parameter/assignment targets.
- Static checking, valid generated JavaScript, runtime behavior, and negative diagnostics.
- No silent data loss for object rest and no invalid `SpreadElement` lvalues.

### 4. Async and resource reliability

- Normalized error objects with category, code, cause, stack, and source context where available.
- Observable handles for background work with join/observation semantics.
- Retry exhaustion must rethrow or return an explicit failure.
- Cancellation-aware timeout for cancellable standard-library operations.
- Minimal `defer`/disposal support applied to streams, readline, subprocesses, and database scopes.

### 5. Developer tooling

- VS Code stdio LSP client with workspace/root handling.
- Correct full or ranged document synchronization with versions and stale-result protection.
- Semantic cross-file definition, references, rename, hover, completion, and signature help.
- Structured diagnostics shared with CLI.
- Parser-backed formatting exposed through LSP and CLI check/diff mode.

### 6. Proof and release hardening

- One version source synchronized across package, compiler, lockfile, grammar/docs, LSP, templates, examples, VS Code metadata, changelog, and publish artifacts.
- Canonical examples and templates have executable checks or explicit environment annotations.
- Fix the currently failing `examples/functions.pln` gate.
- Add a realistic multi-file consumer fixture with visibility, nested imports, npm interop, generated output, and rebuild behavior.
- Add failure-path tests for async rejection, cancellation, cleanup, and source-enriched errors.

## Explicit non-goals

- Full TypeScript-like generics, interfaces, aliases, overloads, variance, or generic inference.
- Structural pattern matching, guards, exhaustiveness checking, or discriminated-union control flow.
- A complete user-facing class system with constructors, methods, fields, visibility, inheritance, and `super` semantics.
- A broad new standard-library expansion, sockets/DNS/TLS, database pooling, or browser bundler implementation.
- A complete ESM-first ecosystem rewrite or support for every npm package.
- A debugger/DAP implementation. Existing source-map generation will be validated, not marketed as source-level debugging.
- Breaking changes to valid existing control-flow, async, recovery, module, or record syntax.

## Implementation order

1. **Contract and inventory:** freeze the compatibility matrix, add the version synchronization check, catalog AST/diagnostic shapes, and convert every known audit probe into a regression test.
2. **Semantic spine:** implement module graph, symbol/export tables, resolution, canonical types, structured diagnostics, and shared APIs. Wire CLI, checker, bundler, and LSP to them before adding syntax.
3. **Safety slice:** repair destructuring and lvalue generation; fix checker traversal, `unknown`/`any`, returns, indexes, assignments, and operators; add normalized async errors, observable tasks, cancellation, retry policy, and disposal.
4. **Tooling:** ship the VS Code LSP client, correct synchronization and workspace invalidation, replace regex navigation, expose formatting, and verify source-map stability.
5. **Proof and release:** execute canonical examples/templates where declared executable, run HTTP/SQLite/multi-file/npm fixtures, validate failure paths, run clean packaging checks, update docs/changelog, and perform a release-candidate audit.

## Release gates

- All release metadata reports exactly `1.1.5` from one source of truth.
- Destructuring conformance covers nested, rest, alias, default, negative, generated-JS, and runtime cases.
- Type/module negatives prove no heterogeneous-list, index, assignment, nested-return, unknown/any, visibility, alias, or collision escapes.
- Async/resource tests cover rejected combinators, background failure observation, retry exhaustion, timeout side effects, cancellation, recovery/finally, and cleanup.
- The packaged VS Code extension starts the LSP client; ranged edits update diagnostics; semantic navigation excludes comments and strings.
- Canonical examples pass check/build/run or carry explicit environment annotations; documentation claims match executable proof.
- `npm pack` followed by clean install/check/build/run works without repository state on supported Node versions.

## Risks and controls

The parser and generator are monolithic, so every semantic change can affect multiple domains. Land conformance tests and shared services before behavior changes. Tightening checker and module rules may reveal programs previously accepted by accident; provide precise diagnostics rather than preserving unsound acceptance. Cancellation and disposal must not claim guarantees for operations that cannot cancel; mark those operations explicitly. Keep generics, classes, structural matching, ESM breadth, and broad library expansion outside this milestone to prevent another partially implemented feature collection.
